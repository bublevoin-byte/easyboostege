# Historical Cycle 8 performance baseline — superseded; not current release evidence

Раздел 19 ТЗ задаёт бюджеты Core Web Vitals. Этот документ сохраняет историческую методику и
наблюдения Cycle 8 только для сравнения. Cycle 11/12 изменили source после той сборки, поэтому все
числа ниже superseded и не являются current release evidence. Текущие artifact/E2E/performance
evidence намеренно недоступны до единственного финального `npm run test:release:aisy`.

Сборка содержит 27 ленивых чанков. В набор ленивых экранов (`ege-mock`, Practice, Прогресс,
Профиль и предметные разделы) не входит код первой загрузки. При старте исполняются оболочка, Сегодня,
экран Слов и компактные Grammar/Exam domain-контракты; презентация Грамматики и её каталог загружаются
лениво. Practice, ЕГЭ, Прогресс, экран Профиля, Ася,
privacy, Voice Tutor, adaptive runtime и тяжёлые предметные модули не запрашиваются страницей.
Static closures top-level routes, Аси, privacy и adaptive runtime входят в отдельно проверяемый
install-cache service worker; глубокие предметные экраны и Voice Tutor кэшируются после явного
использования. Исключение относится только к совместимому обновлению уже установленной версии:
новый worker предзагружает/обновляет executable closure exact EGE mock даже без open-marker, чтобы
не оборвать восстанавливаемый пробник. На чистой установке эта closure остаётся runtime-only и не
входит в `APP_SHELL`. Production package также несёт exact d367 predecessor hashed executable graph.
Все 26 файлов digest-проверенно устанавливаются только в predecessor cache при update. Каждый
действительно predecessor-only файл отсутствует в current/clean-install `APP_SHELL`; пересечение
compatibility graph с shell — ровно два byte-identical current-emitted пути:
`/assets/asya-assistant-1Lybndln.js` (14 642 bytes,
`f2a2e4371e15daa72b46777eb4fe61b4a694a7f3bf573f8a6603947db380d176`) и
`/assets/reading-catalog-contract-HSvgPmNc.js` (13 036 bytes,
`518cc358031b6c9b8a61b615a03515395effe4e5001b6cd6a999280bfcbb8414`). Остальные 24 compatibility
entries остаются вне shell; некоторые из них являются unchanged current lazy outputs, а не
predecessor-only. Compatibility artifact не добавляет predecessor-only код в initial JavaScript.

## Как измеряется

```bash
npm run test:e2e:performance
```

`e2e/performance.test.js` поднимает сервер на свободном порту с файловым хранилищем, создаёт в нём
пользователя с активной подпиской, подтверждает сессию через `/api/v1/me`, открывает приложение в
headless Chrome и собирает записи `PerformanceObserver` до, во время и после прохода по новой
learner-навигации: Practice и её маршрутам Слова, Грамматика, Чтение и Аудирование.

INP считается по худшему взаимодействию, а не по 98-му перцентилю: полевое определение перцентиля
начинает работать после полусотни взаимодействий, а этот проход короткий. Задержка индикатора
проверки ИИ измеряется отдельно, на той же серверно подтверждённой активной сессии с намеренно
медленным ответом провайдера.

Вес первой загрузки снимается на отдельном контексте, **до любой навигации по экранам** и **с
отключённым service worker** (`serviceWorkers: 'block'`). Resource Timing определяет точный набор
initial scripts и их несжатый размер, после чего каждый найденный URL повторно запрашивается у того
же локального production server с `Accept-Encoding: gzip`. Тест суммирует реальные байты response
body и принимает только `Content-Encoding: gzip` либо явно проверенный `identity`. В исторической Cycle 8 сборке
entry занимает 90 262 байта с gzip, а классический `/theme-prepaint.js` — 825 байт identity; итого
91 087 байт, или 89,0 КБ. Оба условия — не осторожность, а требование методики:

- сумма ресурсов, снятая после обхода экранов, включает чанки, которых при старте не было, и меряет
  уже не первую загрузку;
- работающий service worker забирает себе все запросы страницы, и тогда `transferSize` равен нулю,
  `deliveryType` — `cache`, а `encodedBodySize` показывает **несжатый** размер. Байт по сети в таком
  замере нет вообще, а запрос чанка в нём не отличить от попадания в кэш.

Состав первой загрузки закреплён утверждениями теста, а не наблюдением в консоли. Экран `words` и
Grammar/Exam domain обязаны приехать сразу; `screens/grammar.js` и catalog остаются ленивыми в сети,
но входят в отдельный install-time offline closure. Top-level и глубокие ленивые экраны, Asya/Voice Tutor/privacy и
adaptive runtime не имеют права быть запрошены страницей при старте. Отдельный offline-contract
проверяет, какие из них предзагружает service worker, а какие появляются только в runtime-cache;
для exact EGE mock он отдельно различает чистую установку и compatibility pre-cache при обновлении.
Source-only unit не запускает production build и не читает `dist`: единственная candidate-сборка
сама требует наличие каждого source-derived EGE executable в финальном asset map, а post-build
Chromium сверяет точный source → manifest → worker набор, waiting-cache keys и offline SHA bytes.

До Ticket 11 тот же production-замер дал блокирующие **152,7 КБ**. Бюджет не повышался: presentation
Грамматики и catalog были перенесены за существующую lazy-границу, а install-time offline closure
сохранён. Исторический Cycle 8 результат 89,0 КБ подтверждал исправление на тогдашнем собранном `dist/public`, а не
документированное отклонение.

## Исторический baseline до Ticket 11: было и стало

Windows 10, Node.js 22, headless Chrome (системный, не встроенный в Playwright).
«Было» — ветка `production-hardening`, коммит `b33bfd6`, 29 июля 2026 года.
«Стало» — та же ветка, коммит `9b0efda` (последнее изменение frontend), 30 июля 2026 года, три
прогона подряд.

| Показатель | Было | Стало | Бюджет раздела 19 | Итог |
|---|---:|---:|---:|---|
| LCP | 44 мс | 92–100 мс | 2500 мс | в бюджете |
| CLS | 0.000 | 0.000 | 0.1 | в бюджете |
| **INP** | **224 мс** | **56 мс** | **200 мс** | **в бюджете** |
| Индикатор проверки ИИ | 34 мс | 34–36 мс | 200 мс | в бюджете |
| JavaScript первой загрузки | 350 КБ | 81,9 КБ | 150 КБ | в бюджете |

Взаимодействия по убыванию, мс: было **224**, 112, 24, 16, 16 — стало **56**, 24, 24, 16, 16.

Два числа в последней строке требуют оговорки, потому что мерились по-разному. 350 КБ снято старым
способом — с работающим service worker, то есть это несжатые байты, а не сетевые. Сравнимая с ними
величина сегодня — **229 КБ несжатого JavaScript в 26 файлах**; 81,9 КБ — это тот же набор файлов по
сети, со сжатием, как его получает ученик. По бюджету 150 КБ считается сетевая величина: бюджет
спеки задан «по сети». Вторая оговорка — сам состав: раньше при старте приезжал код всех экранов,
теперь пять экранов приезжают чанком при первом переходе, а четыре offline-first экрана остаются
в оболочке ради обещаний раздела 6.1 и учебных настроек.

## Историческая production-сборка 30 июля 2026

Этот раздел сохранён только для сравнения с pre-Ticket11 архитектурой и не является текущим
release evidence. Сервер отдавал `dist/public`, если сборка была, и `public/` иначе. Исторический
прогон 30 июля 2026 года для тогдашней сборки показал **1 файл, 165 КБ без сжатия, 54,5 КБ по сети**
против 26 файлов, 229 КБ и 81,9 КБ в исходном режиме. Исторический сопоставимый Cycle 8 baseline находится в
начале документа: 2 файла и 89,0 КБ по исправленной gzip-request методике. Эти числа нельзя
использовать как текущую release-кандидатуру. Остальные четыре исторических бюджета были в запасе:
LCP 60–92 мс, CLS ≤ 0.001, INP 48–56 мс, индикатор 26–43 мс.

Состав первой загрузки в собранной версии проверяется по манифесту сборки, а не по именам файлов:
Vite переименовывает чанки в хешированные имена, а четыре статических экрана растворяются в точке
входа. Правило от этого не ослаблено — оно проверено мутацией в обе стороны: статический импорт
`screens/reading.js` даёт «при первой загрузке запрошен ленивый экран», перенос
`screens/progress.js` в ленивую загрузку — «экран раздела 6.1 не приехал при первой загрузке».

LCP выросла с 44 до 92–100 мс, и это ожидаемое следствие лечения INP: главный экран раскладывается и
растрируется заранее, под экраном входа, и даёт свой кандидат на LCP. Запас к бюджету 2500 мс
остаётся более чем двадцатикратным, поэтому бюджет не двигался ни в какую сторону.

## Чем на самом деле был занят превышенный INP

> Историческая запись: этот разбор относится к удалённому клиентскому демо-входу до решения
> Reading 2.0. Текущий performance-сценарий не имеет такого входа и использует активную подписку.

Прежняя редакция этого документа объясняла 224 мс синхронной отрисовкой экранов предметных модулей
внутри обработчика клика. **Замер показал, что это неверно дважды.**

Во-первых, дорогое взаимодействие — не переход на экран модуля, а кнопка «Попробовать демо» на
экране входа. Переходы на экраны модулей стоили 16–64 мс при бюджете 200, и ленивые, и оставшиеся
в оболочке.

Во-вторых, обработчик клика там вообще ничего не делал: время обработки 0,2 мс, задержка входа
0,4 мс. Все 207 мс — презентационная задержка, время от конца обработки до следующего кадра. Трасса
Chrome DevTools Protocol (`devtools.timeline`, `gpu.service`, `viz`, `cc`, `skia`) назвала виновника:
поток рендеринга заканчивает работу через 37 мс после клика, а всё остальное время занят графический
процесс — семь сбросов `RasterDecoderImpl::DoEndRasterCHROMIUM::Flush` по 22, 44, 28, 6, 23, 33 и
36 мс. В разогретом состоянии такие же сбросы стоят 0,1–1,0 мс. Это первая растеризация главного
экрана: программный растеризатор SwiftShader впервые встречает набор его примитивов — тени,
градиенты, кольца прогресса — и компилирует под них программы. Не layout, не style, не скрипт и не
шрифты: прогрев `document.fonts.load()` снял 16–24 мс из 224, а скрытые экраны в DOM не
раскладываются и не растрируются вовсе.

Лечение — `prepareScreen(id)` в `public/router.js`: экран, на который ученик уйдёт следующим,
раскладывается и растрируется заранее, под активным, недостижимый для мыши, клавиатуры и
скринридера. Подробности замера и три отброшенные гипотезы —
в `.scratch/frontend-performance-vite/issues/04-split-screen-render.md`.

## Персональный план: локальный baseline Ticket 08

Тот же real-browser прогон включает authenticated переход в персональный план и серверный preview
60-минутного занятия. Замер начинается перед пользовательским действием и заканчивается после
отрисовки forecast/allocation либо первого executable block. На Windows 10, Node.js 22 и headless
Chrome 4 августа 2026 года получено:

| Показатель | Локальный результат | Бюджет | Итог |
|---|---:|---:|---|
| Отрисовка персонального плана | 113 мс | 1500 мс | в бюджете |
| Предпросмотр персонального занятия | 56 мс | 1500 мс | в бюджете |
| LCP / CLS / INP того же прогона | 116 мс / 0.000 / 136 мс | 2500 мс / 0.1 / 200 мс | в бюджете |
| JavaScript первой загрузки по сети | 82.2 КБ | 150 КБ | в бюджете |

Результат — локальная regression baseline, а не production SLO. Сервер использует временное
файловое хранилище, AI route — локальный delayed stub, внешние API и production данные не вызываются.
