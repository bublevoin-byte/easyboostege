# Базовая линия производительности

Раздел 19 ТЗ задаёт бюджеты Core Web Vitals. Этот документ фиксирует, чем и на чём они измеряются
и какими были до работы над ленивой загрузкой frontend — чтобы улучшение можно было доказать
числами, а не впечатлением, и чтобы регрессию было с чем сравнить.

## Как измеряется

```bash
npm run test:e2e:performance
```

`e2e/performance.test.js` поднимает сервер на свободном порту с файловым хранилищем, открывает
приложение в headless Chrome и собирает записи `PerformanceObserver` до, во время и после прохода
по экранам, которые ученик открывает первыми: демо-вход, затем «Слова», «Грамматика», «Чтение»,
«Аудирование» с возвратом на главный экран.

INP считается по худшему взаимодействию, а не по 98-му перцентилю: полевое определение перцентиля
начинает работать после полусотни взаимодействий, а этот проход короткий. Задержка индикатора
проверки ИИ измеряется отдельно, на настоящей сессии с намеренно медленным ответом провайдера —
в демо-режиме ответ приходит локально, и индикатор не показывается вовсе.

## Почему INP превышен

Одно взаимодействие вдвое хуже следующего за ним, а остальные три на порядок быстрее. Это первый
переход на экран предметного модуля. `public/index.html` подключает двадцать классических скриптов
через `<script defer>`, среди них `app.js` весом 289 КБ с кодом всех экранов сразу. Классический
скрипт нельзя загрузить по требованию, поэтому вся отрисовка экрана происходит синхронно внутри
обработчика клика, и браузер не может отдать кадр, пока она не закончится.

## Целевое состояние

| Показатель | Цель |
|---|---|
| INP | не более 200 мс — бюджет раздела 19 |
| JavaScript первой загрузки | не более 150 КБ по сети |
| Экран предметного модуля | отдельный запрос при первом переходе, ничего при повторном |

LCP, CLS и задержка индикатора проверки ИИ уже в бюджете и не должны из него выйти.
