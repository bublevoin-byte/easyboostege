# ADR 0001 — Сборка frontend и целевой фреймворк

**Дата:** 29 июля 2026 года
**Статус:** принято
**Закрывает:** раздел 5.1 ТЗ подготовки к production

## Контекст

Раздел 5.1 ТЗ предлагает два взаимоисключающих варианта frontend: модульный JavaScript без
фреймворка либо React/Vue/Svelte с Vite. Пункт оставался открытым, потому что выбор откладывали.

Одновременно раздел 19 не выполняется: INP составляет 224 мс при бюджете 200 мс, по сети приезжает
350 КБ JavaScript, а первый экран ждёт загрузки всего учебного контента. Двадцать классических
скриптов подключены через `<script defer>` и обмениваются данными через глобальные имена, поэтому
ни ленивой загрузки, ни разбиения на чанки сейчас нет.

## Решение

**Целевой фреймворк — React.** Выбран владельцем: самая большая экосистема и проще найти помощь,
что важнее размера runtime для проекта, который будет развиваться дальше.

**Сборщик — Vite,** и он въезжает раньше фреймворка. Порядок работ:

1. Перевести существующий код на нативные ES-модули — без сборщика и без фреймворка.
2. Ввести ленивую загрузку экранов через динамический `import()` и закрыть раздел 19.
3. Подключить Vite как сборщик: бандлинг, минификация, хешированные имена файлов.
4. Мигрировать экраны на React по одному — отдельным этапом, уже на готовой инфраструктуре.

## Почему такой порядок

Шаги 1–2 закрывают раздел 19 нативными средствами браузера и не добавляют ни одной зависимости.
Если шаг 3 придётся отложить — например, владелец не захочет новую зависимость перед релизом —
требования производительности всё равно выполнены. Обратный порядок этого не даёт.

Миграция на React последним шагом означает, что 261 существующий тест и все E2E-сценарии остаются
рабочими на протяжении подготовки к запуску. Переписывание девяти предметных модулей, 148 КБ
разметки и всех браузерных сценариев прямо перед ограниченным запуском — риск регрессий, который
проект в этой точке не окупает.

## Последствия

- Появляется новая зависимость `vite` в `devDependencies`. Установку выполняет владелец.
- `public/` остаётся каталогом исходников. Сборка кладёт результат в `dist/public`.
- CSP считает хеши инлайновых скриптов по фактически отдаваемому `index.html`, поэтому сервер
  должен брать разметку из того же каталога, что и статику.
- Service worker кэширует список файлов и требует обновления при смене имён ассетов.
- React в этом решении зафиксирован как направление, но ни одной строки React-кода пока не пишется.
