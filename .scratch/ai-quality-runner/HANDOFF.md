## Следующая задача

**Написать раннер методической проверки ИИ.** Это пункт 2 раздела 11.2 ТЗ, он не выполнен,
и без него раздел 11 стоит на нуле из 28.

### Что уже готово

`quality/writing-fipi-stubs.json` — **21 работа с текстом**, набранным владельцем со сканов ФИПИ
и выверенным: объём каждой сходится с подсчётом эксперта в пределах пяти слов, абзацы
восстановлены по сканам, дубли убраны.

### Чего не хватает

Ни у одной работы нет поля `aiRuns` — то есть результатов прогона ИИ. Их нечем получить:
скрипта, который берёт работу, зовёт ту же серверную операцию, что и приложение, и записывает
результат, не существует.

`scripts/ai-quality-report.js` (`npm run quality:check`, `npm run quality:release`) **не обращается
к ИИ вообще** — он считает метрики по готовым `aiRuns`. Не перепутать.

### Что должен делать раннер

1. Для каждой работы из набора вызвать ту же операцию, что и приложение
   (`ai/writing.js`, `buildWritingPrompt` / `parseAndValidateWritingReview`), **минимум дважды** —
   метрика стабильности из §11.3 требует сравнения повторных прогонов.
2. Записать в работу `aiRuns: [{valid, total, criteria, detectedErrors, explanationApproved,
   britishEnglishApproved, injectionResisted}]`. Форма — как в `quality/engineering-smoke.json`.
3. Ключи критериев обязаны совпадать с ключами в `human.criteria`: в наборе ФИПИ это `k1`…`k3`
   для задания 37 и `k1`…`k5` для задания 38, а не `task`/`organisation`/`language`, как в
   инженерной заглушке. `ai/quality.js` сопоставляет их по имени.
4. Быть прерываемым и докладывать прогресс: прогон платный, и падение на девятнадцатой работе
   не должно стоить восемнадцати предыдущих.
5. Уважать бюджеты из `ai/operations.js` — там у каждой операции свои лимиты.

Часть метрик §11.2 требует человеческого суждения (корректность объяснений). Решить честно:
либо поле заполняется отдельным проходом человека, либо метрика помечается как неизмеренная.
**Не подставлять `true` по умолчанию** — это превратит проверку в самообман.

### Чего раннер не закроет

Релизный гейт требует 20 работ задания 37 и 30 задания 38; есть 12 и 9. `--release` откажет
по объёму, и это правильно. Отчёт по расхождениям при этом будет содержательным.

## Ловушки этой машины, проверенные на своей шкуре

- **Путь содержит кириллицу и пробел.** В PowerShell брать в кавычки, git запускать как
  `git -C "<путь>" ...`, не через `cd`.
- **Многострочные here-string в PowerShell ломаются.** Сообщение коммита писать в файл во
  временном каталоге и делать `git commit -F <файл>`.
- **Playwright использует системный Chrome**, встроенный headless shell не установлен. Свои
  скрипты замера запускать с `executablePath`, как это делает `chromeExecutable()` в тестах.
- **`Select-Object -First N` рвёт конвейер**, и node падает с ненулевым кодом на ровном месте.
  Не принимать это за ошибку скрипта.
- **`/tmp` в Git Bash и в node — разные каталоги.** Использовать каталог-черновик сессии.
- **`.env` на машине отсутствует**, ключей провайдера нет. Прогон ИИ отсюда невозможен, пока
  владелец их не положит. Ключи — его дело: никогда не просить значение, работать с именем.

## Правила, которые нельзя нарушать

- **Push в `production-hardening` разворачивает staging** через GitHub Actions. Отсчёт
  семидневного soak идёт с 30 июля 2026 года, и лишний push его сбрасывает. Отправлять только
  по слову владельца. Сейчас не отправлено 6 коммитов — это осознанно.
- **Деплой, установка пакетов, платные прогоны — действия владельца.** Агент их не начинает сам.
- **Ни один тест не удаляется и не ослабляется** ради зелёной сборки. Порог двигается только
  вместе с записанной причиной.
- **Секреты**: только имена переменных, никогда значения.
- Перед коммитом: `npm run lint`, `npm run check`, `npm test` (ожидается 264 / 263 / 1 / 0).
