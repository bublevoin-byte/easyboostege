# 03 — Ленивая загрузка экранов через динамический import()

Status: done
Blocked by: 02
Spec: .scratch/frontend-performance-vite/spec.md#42-ленивая-загрузка-экранов

## Что сделать

Сделать так, чтобы код предметного экрана приезжал по требованию, при первом переходе на него, а не
при старте приложения. Первая загрузка тянет только оболочку: маршрутизацию, хранилище, общие
компоненты, авторизацию, синхронизацию и главный экран.

`public/app.js` весит 289 КБ и содержит код всех экранов сразу. Его нужно разрезать: код каждого
экрана переезжает в свой модуль, который `router.js` загружает динамическим `import()`.

## Что оставил после себя тикет 02

`public/main.js` — единственная точка входа. Она импортирует двадцать модулей в прежнем порядке и
раскладывает имена по `window` через `exposeGlobals(namespace)`: каждое имя становится геттером,
а не копией значения, потому что состояние экранов переприсваивается по ходу работы.

**Этот же механизм работает и для чанка:** модуль экрана, загруженный динамическим `import()`,
отдаёт свой namespace, и загрузчик вызывает на нём `exposeGlobals`. До загрузки чанка его имён на
`window` нет — и не должно быть, потому что обработчик, который их зовёт, существует только внутри
разметки, отрисованной этим же экраном.

`scripts/check-inline-handlers.js` подключён к `npm run check` и проверяет, что каждое имя из всех
144 обработчиков разрешимо. **Его придётся научить новому:** имя теперь может приходить из
лениво загружаемого модуля, поэтому проверка должна разбирать экспорты всех модулей экранов
статически, а не смотреть, что лежит на `window` при старте. Проверка обязана остаться строгой —
она единственное, что ловит потерянный обработчик до того, как его потеряет ученик.

Замер после тикета 02: **INP 208 мс** при бюджете 200, JavaScript по сети 358 КБ.
Базовая линия была 224 мс и 350 КБ.

## Карта экранов

`public/index.html` содержит семнадцать элементов `.screen`. Оболочка — то, что грузится сразу:

| `scr1` | Главная | оболочка |
| `scr14`, `scr15` | Нет сети, пусто | оболочка |

В `public/app.js` расставлены маркеры `/* legacy block 1..12 */` — строки 1, 374, 403, 427, 465,
932, 1495, 1897, 2339, 2472, 2483. Они примерно соответствуют предметным областям и годятся как
отправная точка, но границы определяй по вызовам, а не по маркерам.

## Границы

**Входит:**

- Вынести из `app.js` код экранов девяти предметных модулей: слова, грамматика, чтение,
  аудирование, письмо, говорение, экзамен, прогресс, профиль.
- `router.js`: `tab(id)` становится асинхронным по сути — сначала грузит чанк экрана, затем
  показывает. Уже загруженный экран не ждёт ничего.
- Состояние загрузки из `components.js` показывается, только если чанк не пришёл за 100 мс:
  на быстром соединении ученик не должен видеть мигание.
- Ошибка загрузки чанка даёт типизированное состояние с повторной попыткой, а не пустой экран.
  Офлайн-поведение — как у остальных операций раздела 6.2.
- `public/service-worker.js`: чанки экранов кэшируются при первой загрузке, чтобы офлайн-запуск
  открывал уже виденные экраны. `/api/` из кэша по-прежнему не отвечает.

**Не входит:**

- Разделение синхронной отрисовки на кадры — тикет 04.
- Вынос учебных данных в JSON — тикет 05.
- Vite — тикет 06. Здесь используется только нативный `import()`.

## Что разошлось с постановкой

**Три экрана из восьми остались в оболочке, и это не отступление, а требование.** Постановка
делила экраны на «оболочку» и «чанки» по тому, что ученик открывает первым, и относила «Слова»,
«Грамматику» и «Прогресс» к чанкам. Это противоречит разделу 6.1 ТЗ, который обещает без сети
словарные карточки, интервальное повторение, встроенные грамматические тесты и просмотр
сохранённого прогресса. Ученик может уйти в офлайн, ни разу не открыв эти экраны, — и обещание
всё равно наступает, а чанка нет ни в сети, ни в кэше.

Первым это поймал не разбор, а `e2e/demo.test.js`: контекст офлайн-блока создаётся с
`serviceWorkers: 'block'` (строка 191), то есть тест намеренно отказывается принимать кэш как
доказательство офлайн-работы. Требование он проверяет строже, чем «в кэше что-то лежало».

Цена решения измерена, а не оценена: первая загрузка со всеми восемью экранами в чанках —
51,6 КБ JavaScript по сети; с тремя экранами в оболочке — около 74 КБ. Бюджет спеки — 150 КБ,
и он выполняется с запасом вдвое. Дилеммы «офлайн против веса» здесь не оказалось.

Правило закреплено тестом: `test/security-restriction`-проверка порядка импортов теперь утверждает
оба списка — какие три экрана обязаны быть в оболочке и какие пять обязаны остаться ленивыми, —
и что ни один экран не попал в оба списка сразу. `scripts/check-inline-handlers.js` научен считать
разрешимыми имена экрана, подключённого статически, а не только через `screens.js`.

**INP по-прежнему превышен: 216 мс при бюджете 200.** Но распределение изменилось принципиально:
базовая линия давала 224, 112, 24, 16, 16 мс, сейчас — 216, 64, 24, 16, 16. Все взаимодействия,
кроме одного, стали заметно быстрее; худшее осталось прежним. Это ровно то, чем занимается
тикет 04: отрисовка экрана всё ещё целиком лежит внутри обработчика клика, и браузер не может
отдать кадр, пока она не закончится. Ленивая загрузка сама по себе этого не лечит.

**`wPick` не попал в список экспортов** `screens/words.js` при переносе — обработчик
`onclick="wPick(this,'','')"` остался бы неразрешимым. Поймала проверка обработчиков, ради которой
она и заведена; в браузере это была бы молча неработающая кнопка ответа.
