## Почему needs-info

Тикет добавляет новую зависимость `vite` в `devDependencies`. Установку пакетов выполняет владелец,
а не агент. Пока владелец не выполнит `npm install`, тикет не берётся в работу.

Тикеты 01–05 закрывают раздел 19 нативными средствами браузера и от этого тикета не зависят: если
владелец решит не добавлять зависимость перед релизом, требования производительности всё равно
выполнены. Vite здесь — про качество сборки и про инфраструктуру для будущей миграции на React.

## Что сделать

Собрать `public/` в `dist/public` с бандлингом, минификацией, хешированными именами файлов и
автоматическим разделением динамических импортов на чанки.

`public/` остаётся каталогом исходников: все существующие тесты читают именно эти файлы и должны
продолжать читать их.

## Границы

**Входит:**

- `vite` в `devDependencies`, `vite.config.js` с `root: 'public'` и выводом в `dist/public`.
- `npm run build:frontend` запускает сборку Vite и сохраняет нынешнюю проверку целостности ассетов.
- `server.js` отдаёт `dist/public`, если каталог существует, иначе `public/`. Тот же каталог
  используется для чтения `index.html` под CSP и под SPA-fallback — иначе хеши инлайновых скриптов
  посчитаются по одной разметке, а отдастся другая.
- `public/service-worker.js` перестаёт хранить список имён файлов вручную, если имена стали
  хешированными: список берётся из манифеста сборки.
- `.gitignore` уже игнорирует `dist/` — проверить, что это осталось верным.
- `README_DEPLOY.md` и `.github/workflows/ci.yml`: шаг сборки перед запуском в production.

**Не входит:**

- React и любой другой фреймворк. Ни одной строки компонентного кода.
- Изменение исходников ради удобства сборщика сверх необходимого.
- Деплой куда бы то ни было.

## Результат

Сборка снимает треть сетевого веса первой загрузки: **81,9 КБ в 26 файлах на исходниках против
54,5 КБ в одном файле на сборке** при бюджете 150 КБ; несжатого JavaScript — 229 КБ против 165 КБ.
Остальные бюджеты в обоих режимах в запасе: LCP 92 и 64 мс, CLS 0.000 и 0.001, INP 48 и 56 мс,
индикатор проверки ИИ 33 и 44 мс. Пять ленивых экранов остались пятью отдельными чанками, три
экрана раздела 6.1 вошли в точку входа.

## Что разошлось с постановкой

- **Проверка состава первой загрузки переехала с имён файлов на манифест сборки, и это оказалось
  строже прежнего.** Vite не просто переименовывает чанки — три статических экрана он растворяет в
  точке входа, и файла `screens/words.js` в сборке не существует вовсе. `e2e/performance.test.js`
  теперь сопоставляет экран с файлом по `dist/public/asset-manifest.json` (на исходниках
  соответствие тождественно) и дополнительно требует, чтобы ни один ленивый экран не лежал в одном
  файле с экраном оболочки — иначе «не запрошен при старте» было бы недостижимо, а не выполнено.
  Правило проверено мутацией в обе стороны на живой сборке: статический импорт `screens/reading.js`
  даёт «при первой загрузке запрошен ленивый экран», перенос `screens/progress.js` в ленивую
  загрузку — «экран раздела 6.1 не приехал при первой загрузке».

- **Имя кэша service worker перестало быть числом, которое поднимают руками.** Постановка требовала
  только брать список из манифеста, но `easyboost-static-vNN` рядом с генерируемым списком — это
  ровно тот забытый бамп, о котором предупреждал `README_DEPLOY.md`. Имя считается по самому списку
  (FNV-1a), поэтому в сборке любое изменение содержимого меняет хеш в имени файла, а значит и имя
  кэша. Список для исходников остался в файле — сервер отдаёт `public/`, когда сборки нет, — но
  `npm run build:frontend` сверяет его с графом статических импортов `main.js` и падает при
  расхождении; проверено удалением `/task-bank.json` из списка.

- **`test/http-smoke.test.js` пришлось научить брать точку входа из отданной разметки.** Он проверял
  сжатие на `/app.js`, а в сборке такого файла нет: CI собирает frontend до тестов, и проверка
  молча измеряла бы SPA-fallback вместо скрипта. Теперь она читает `<script src>` из ответа `/` и
  сравнивает сжатый ответ с несжатым — то есть проверяет тот файл, который страница действительно
  грузит, в обоих режимах. Ни одного утверждения не убрано.

- **`manifest.json` и `pwa-icon.svg` намеренно оставлены без хеша.** Vite по умолчанию переименовал
  и их, а `e2e/demo.test.js` проверяет `link[rel=manifest]` ровно как `/manifest.json`, и
  `test/http-smoke.test.js` запрашивает его по этому адресу. Оба файла меняются вместе с разметкой,
  которая отдаётся с `Cache-Control: no-store`, так что хеш им ничего не давал.

- **Сборка идёт в `dist/public.building` и встаёт на место последним шагом.** Сервер решает, что
  отдавать, по наличию `dist/public/index.html`; недособранный каталог он отдал бы наравне с полным
  — без service worker и без проверенной целостности. Обнаружено на мутации, где сборка падала
  после запуска Vite.

- **`.github/workflows/ci.yml` перестроен так, чтобы оба пути были зелёными.** Раньше сборка шла до
  тестов, и весь набор проверял только собранную версию. Теперь `npm test` и первый Chrome E2E идут
  по исходникам, затем `npm run build:frontend`, затем тот же Chrome E2E и мобильные профили — по
  сборке, то есть по тому, что уезжает в production. Лишнего времени это не стоит.

- **`Dockerfile` не тронут, и это осознанно.** `vite` — dev-зависимость, а образ ставит
  `npm ci --omit=dev`, поэтому собирать внутри образа нечем. `.dockerignore` `dist/` не исключает,
  так что собранный на хосте каталог попадает в образ как есть; порядок «`npm run build:frontend`
  до `docker compose build`» записан в `README_DEPLOY.md` и `RELEASE_CHECKLIST.md`. Многостадийная
  сборка образа — отдельная задача, в границы этого тикета она не входила.
