# 04 — Довести INP до бюджета: дорогое взаимодействие — вход в демо, а не переход на экран

Status: ready-for-agent
Blocked by: 03
Spec: .scratch/frontend-performance-vite/spec.md#42-ленивая-загрузка-экранов

## Постановка исправлена по факту замера

Первая редакция этого тикета — и запись в ТЗ, из которой она выросла, — утверждали, что бюджет
раздела 19 съедает «синхронная отрисовка экранов предметных модулей». **Это неверно.** Замер каждого
взаимодействия по отдельности, после тикета 03:

```
«Попробовать демо»          208 мс   (обработка 0 мс, задержка входа 1 мс)
Слова (в оболочке)           64 мс   (обработка 0 мс, задержка входа 0 мс)
Грамматика (в оболочке)      32 мс   (обработка 0 мс, задержка входа 0 мс)
Чтение (ленивый)             16 мс   (обработка 0 мс, задержка входа 0 мс)
Аудирование (ленивый)        16 мс   (обработка 0 мс, задержка входа 0 мс)
Чтение (повтор)              16 мс
Аудирование (повтор)         16 мс
```

Переходы на экраны модулей укладываются в бюджет с четырёхкратным запасом — и ленивые, и те, что
остались в оболочке. Единственное взаимодействие вне бюджета — **кнопка «Попробовать демо»** на
экране входа.

И его профиль говорит, где искать. `processingEnd - processingStart` равно нулю: обработчик клика
сам по себе не работает почти ничего. `processingStart - startTime` — 1 мс: браузер не был занят,
когда пришёл клик. Значит все 207 мс — это **presentation delay**, время от конца обработки до
следующего кадра. Работа не в обработчике, а в том, что браузер делает после него: layout, style,
paint. Либо в том, что обработчик поставил в микрозадачу или таймер и что попало в то же окно
взаимодействия.

Вероятная причина, но проверь её, а не поверь: `public/index.html` — это 148 КБ разметки с
семнадцатью экранами в DOM одновременно. Клик по «Попробовать демо» первый раз показывает
`scr1`, и браузер впервые считает layout и рисует это поддерево вместе со всеми плитками, кольцами
прогресса и полосами. Первый layout большого скрытого поддерева стоит дорого.

**Отсюда следует, что «разнести отрисовку по кадрам» может не помочь.** Разбиение на кадры лечит
занятый обработчик, а он здесь пустой. Начни с замера — Chrome DevTools Protocol через Playwright
даёт трассу, в которой видно, что именно занимает эти 207 мс: recalculate style, layout, paint или
скрипт. Только потом выбирай лечение.

## Задача

INP ≤ 200 мс на замере `npm run test:e2e:performance`, без ослабления бюджетов и без изменения того,
что ученик видит.

## Границы

**Входит:**

- Диагностика: чем именно заняты 207 мс презентационной задержки на входе в демо.
- Лечение по результату диагностики. Возможные направления, ни одно не предписано:
  разгрузить первый layout экрана `scr1`; не держать все семнадцать экранов в DOM сразу;
  отделить переключение экрана от наполнения в `router.js`; убрать работу, которую `startDemo()`
  ставит в микрозадачу сразу после клика.
- Замер до и после, с разбивкой по взаимодействиям, а не одним числом.

**Не входит:**

- Изменение бюджетов в `e2e/performance.test.js`. Бюджеты раздела 19 берутся из ТЗ и не двигаются.
  Если бюджет не достигнут — это результат, а не повод подвинуть порог.
- Вынос учебных данных в JSON — тикет 05. Он уменьшит вес, но презентационная задержка первого
  кадра — не про вес по сети.
- Косметика интерфейса. Ученик не должен заметить ничего, кроме скорости.
- Изменение разметки экранов ради удобства замера.

## Файлы

Заранее не определены — зависят от диагностики. Наиболее вероятны:

- `public/index.html` — если дело в первом layout семнадцати экранов
- `public/router.js` — если помогает отделить переключение от наполнения
- `public/app.js` — `startDemo()` и отрисовка главного экрана
- `public/components.js` — если нужен общий помощник
